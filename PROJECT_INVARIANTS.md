# Project invariants

User-confirmed design rules. Implementation gaps are tracked in [TODO.md](TODO.md); these rules do not imply all behavior is implemented.

- A boundary is the unit of processing and persistence: it owns inventory, scanning, judgments, evidence, and their stored results. Reporting uses the same grouping. A scope identifies the logical source; a scan target identifies an immutable source version.
- Scan, judgment, and extraction update inventory, report, and credential state by directly mutating their owned in-memory Pydantic objects; routine updates and merges do not copy models to preserve previous in-memory state. At checkpoints, Boundary functions persist each available document completely in the workspace, using atomic replacement per file; a checkpoint is not a multi-document transaction. Exceptions: Titus writes its cumulative datastore during scanning, and the extractor writes retained evidence bytes before Boundary checkpoints their extraction metadata.
- Inventory keeps only the latest selected scan target per scope. Successful discovery replaces the target list, retaining scan results for unchanged target IDs and starting newly selected targets pending. Historical credentials and occurrences remain independent of inventory history. Discovery must complete successfully before updating inventory. Discovery exceptions propagate to the user, leaving the previous inventory unchanged; do not store discovery errors or partial inventory.
- Each credential occurrence path identifies the exact immutable source version and file, allowing historical reads without historical inventory. Content readers resolve and read requested paths using their configured backend, without receiving or validating a boundary reference.
- Each boundary keeps one cumulative Titus datastore across scan runs, retaining past scan data as new scan targets are added. Inventory replacement does not reset it.
- For each boundary, exactly one command operation may own it at a time. The operation acquires that boundary's lock before loading persisted state and holds ownership through its inventory, scan, judgment, or extraction work and resource cleanup. A competing command cannot work on the same boundary. One command invocation may process different boundaries concurrently.
- While owned, each boundary creates one scanner, one judge, and one extractor for the command. Each boundary scans its targets sequentially, with at most one Titus invocation at a time. Titus inherits the boundary lock descriptor so a surviving child continues to exclude another command.
- Titus enables all supported extraction formats, caps each extracted file at 100 MB, and limits each scanned file to 512 KiB (524,288 bytes). These flags are configured in config.yml.
- Titus's internal parallelism remains available; there is no application-level scanner pool within a boundary.
- Scan publishes candidates after scan attempts finish and the boundary-wide Titus export succeeds. Failed scan targets mark the report incomplete but do not block judgment and extraction of available findings. Every occurrence retains a self-contained source path.
- VALID and UNKNOWN judgments enable evidence extraction; extraction failures preserve the saved judgment for retry without rejudgment. Retained evidence is never overwritten. On later runs, check only that its file exists and report missing files without automatic replacement; do not verify contents, size, or hash.
- Instruct the judge to prefer the first occurrence's file; it may read additional occurrence files. Extraction independently reads and retains only the first occurrence's file.
- Scan, judgment, and extraction commands run in separate processes. Content readers do not cache resolved locations or retrieved files; each read fetches the requested source. No whole-image, repository, archive, or general blob cache is allowed. Temporary download scratch and retained evidence are separate from caching.
- By convention, runtime settings (workspace, Titus, LLM, backend, and exclusion paths) belong in config.yml, and secrets in environment variables or .env. Do not enforce source separation with custom filtering. Model API keys with Pydantic SecretStr and unwrap them where services pass them to clients or subprocesses. Resolved application configuration is available globally; services obtain their settings and secrets where needed rather than receiving them through Workspace. The deduplicator and Titus obtain exclusions directly from global configuration; Boundary does not hold or pass an exclusion policy. Exclusions load once per run at first use and are shared across boundaries.
- Changed exclusion patterns apply during subsequent scan processing; they do not retroactively filter or delete saved credentials, judgments, or evidence.
- Artifactory requires HTTPS and uses an identity or access token as standard Bearer authorization. Same-origin redirects retain authorization; cross-origin redirects may proceed without forwarding credentials.
- This is a single-user project with one existing workspace. Every change to its persisted format includes migrating that workspace in the same task, preserving its accumulated results and evidence. Do not build compatibility machinery for a hypothetical installed user base.
- Extraction models, evidence retention functions, and the extractor live in the dedicated extract module; orchestration owns eligibility and persistence. Keep module responsibilities clear and avoid circular dependencies; specific import directions are implementation choices.
