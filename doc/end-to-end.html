00 / Vocabulary

The nouns that organize the scanner.

These terms describe ownership and identity. A boundary is the unit of processing and persistence, owning its workflow and stored results; a scope describes a logical source; a target is one immutable version of that scope. Credentials retain backend locators rather than target objects.

Boundary

The unit of processing and persistence: currently an Artifactory repository, or a future Git organization. It owns inventory, scanning, judgments, evidence, and their stored results, including one cumulative Titus datastore, report, credential document, and evidence area. Reporting uses the same grouping.

ScanScope

The logical source being monitored, such as a Docker image, Git repository, or package. Its logical identity remains stable while its selected versions change over time.

ScanTarget

One immutable version of a scope: for example a selected child manifest, commit, or package artifact. It is the inventory and Titus scheduling unit. Its scan target identity is immutable; its scan result is lifecycle state.

Backend

The adapter for a source system. It discovers boundaries and targets, supplies Titus arguments, and interprets backend locators to return source bytes and metadata.

Inventory

The manually refreshed document for one boundary. It keeps only the latest selected scan target per scope and its execution result. Historical credentials and occurrence paths remain independent of inventory history.

Locator

An opaque, complete backend path for one source occurrence. It is persisted inside a credential occurrence and interpreted by the ContentReader and its associated backend. It identifies the exact immutable source version and file, so historical reads require no historical inventory.

Credential and occurrence

A credential is one deduplicated detected value identified by credential_id. One credential may have many occurrences, each retaining a distinct locator where it appeared.

Report and datastore

The boundary datastore is Titus's persistent incremental state. The final boundary export is report.json, retaining raw cumulative findings before normalized credential publication.

Judgment

The assessment attached to a credential: PENDING, VALID, INVALID, UNKNOWN, or ERROR. VALID and UNKNOWN enable new evidence retention.

Evidence

A retained first-occurrence source file for a credential judged VALID or UNKNOWN. Bytes live under the boundary evidence directory; credentials.json stores output path, size, hash, and status.

Operator sequence: invoke inventory, scan, judge, or extract. Workspace applies that command across persisted boundaries concurrently. For each boundary, the operation acquires the boundary-local OS lock before loading documents and holds it through cleanup. A competing command cannot work on the same boundary. Judge never extracts evidence; Extract only consumes saved VALID or UNKNOWN judgments.

The Boundary is the mutable aggregate. Its inventory, report, and credentials are checkpointed together; there is no scheduler checkpoint or cross-boundary handoff.

Shared context, not additional pipeline payloads: AppConfig configures services; the Boundary derives its own storage paths from its directory; BackendAdapter and ContentReader are service ports, not serialized models. Artifactory requires HTTPS and uses Bearer authorization; same-origin redirects retain it while cross-origin downloads proceed without credentials.

02 / Inside each stage

Model inputs and outputs at operation level.

The graph above follows persisted documents. These smaller contracts show what each operation actually accepts and returns. Signatures below omit self; arrows describe types, not executable examples.

Inventory · backend-owned discovery

BackendAdapter.discover_boundaries()
  → tuple[boundary_id, ...]
BackendAdapter.inventory(boundary_id)
  → ScanTargetInventory

The workspace owns one configured backend. It first discovers backend boundary IDs, reconciles them with persisted boundary.json records, and then initializes, refreshes, or marks each Boundary absent under that boundary's lock.

  1. Discover an Artifactory repository boundary and its logical Docker image scopes.
  2. Select the newest manifest/platform by timestamp in the backend and create immutable ScanTarget values.
  3. Merge by canonical target ID; save current targets to scantargets.json and enrollment/availability to boundary.json.

Implemented: inventory keeps only the latest selected scan targets. Successful discovery replaces the selected list; absent scopes and old versions are removed. An unchanged scan target reuses its result; a newly selected scan target starts pending. Historical credentials, occurrence paths, judgments, and evidence survive inventory replacement. The boundary keeps one cumulative Titus datastore across scan runs; inventory replacement does not reset past scan data. Occurrence reads are independent of inventory: the ContentReader interprets each immutable path directly.

Implemented: backend boundary discovery runs before scan-target initialization or refresh, enrolling repositories in an empty workspace and repositories added later. A successful authoritative listing marks omitted registered boundaries absent, removes their current scantargets.json, and retains their historical report, credentials, evidence, and datastore. If they reappear, new scan targets are written before the record becomes available. Boundary-list or per-boundary discovery failures leave existing records and scan targets unchanged.

Implemented: catalog and tag-list pagination completes before target selection. Their payloads must be objects containing arrays of non-empty names; malformed JSON or shapes raise. Explicit empty arrays are successful discovery and may produce an inventory with no targets.

Owner: backend/ boundary and target discovery plus merge rules, coordinated by orch/workspace.py and orch/boundary.py. An available empty repository has an empty scantargets.json; an absent repository has no current scan-target document.

The scanner mutates the boundary-owned target's ScanTargetResult and returns no replacement. The Artifactory Docker adapter supplies Titus with the boundary's repository key and the exact selected image reference scope.image@scope.digest. The immutable child-manifest digest is used rather than a mutable tag or the parent/root digest; platform selection has already occurred during inventory discovery. Unsupported scope types fail permanently without starting Titus. All target invocations write to the same boundary datastore. Configured Titus arguments enable all supported extraction formats (--extract all), cap each extracted file at 100MB (--extract-max-size), and set the per-file scan limit to 512 KiB (--max-file-size 524288). Conversion normalizes backend locators, groups credentials, applies exclusions, and preserves every source occurrence. After scan attempts finish and the boundary-wide export succeeds, failed scan targets mark the report incomplete but do not block judgment and extraction of available findings.

Owner: scan/ detects/converts; orch/ checkpoints and publishes. Unresolvable locations stay in the raw report plus diagnostics, not in unresolved judge candidates.

Judge · credential in, judgment out

FindingJudge.judge(
  credential: Credential, content: ContentReader
) → JudgmentResult

mutate credential.judgment and persist the current document

Orchestration validates the document boundary. Credentials persist occurrence paths only. The ContentReader, together with its configured backend, interprets each immutable path and returns exact bytes plus source metadata; it receives no boundary reference and does not validate repository membership or need historical inventory targets. The boundary owns the reader’s lifecycle and persisted results. The agreed instruction is to prefer the first occurrence's file, while allowing additional occurrence reads. The reader does not cache resolved locations or retrieved files; each read retrieves source bytes independently.

JudgmentResult.verdict is PENDING | VALID | INVALID | UNKNOWN | ERROR. The result also carries reasoning. A verdict is not user acceptance or mitigation.

Boundary.judge() returns the number of attempted judgments. It only updates saved judgment results. Evidence extraction is a separate Boundary.extract() operation.

Owner: judge/ assesses; orch/ saves each judgment to the latest credential checkpoint.

mutate credential.extraction and persist the current document

For a VALID or UNKNOWN credential, orchestration selects only occurrences[0].locator. Extraction reads the exact backend locator independently of judgment. Additional occurrence files read by the judge do not become retained evidence. Python writes and hashes the first occurrence's file, then checkpoints ExtractionResult.

Boundary.extract() selects eligible credentials once and returns the number of attempted extractions, including handled attempts that save ERROR. RETAINED credentials are audited separately with a file-existence check on every extraction run, including when no new extraction is pending, and do not contribute to the count. Missing files are reported without automatic replacement; contents, size, and hash are not verified. Missing evidence is logged with its boundary, credential, and stored path; the RETAINED metadata remains unchanged. Retrieval/write errors keep the saved VALID or UNKNOWN judgment.

Owner: extract/evidence.py owns destinations, existence checks, and retention; orch/ owns eligibility, session lifetime, and persistence. The dedicated extract/ module owns the extractor, evidence functions, and ExtractionResult in extract/models.py.

Return value ≠ persisted output. Each command runs its requested stage across persisted boundaries concurrently. Inventory returns the refreshed-boundary count; Scan returns the completed-boundary count; Judge and Extract return their selected credential counts. Document updates shown in the graph are saved checkpoints, not all CLI return values. Protocol declarations describe contracts and are not themselves implementations.

Execution / Persisted obligations, exclusive live ownership

One boundary can owe work in several phases.

The runtime Boundary is the mutable aggregate for one exclusively owned boundary. Workspace owns one backend and constructs unloaded Boundaries from persisted boundary.json records; services read resolved global configuration directly and the deduplicator and Titus obtain exclusions directly from global configuration, loaded once per run at first use. Each source-dependent Boundary operation acquires ownership before reading scan targets, report, and credentials. Those documents are changed in memory and written together at Boundary-owned checkpoints. There is no cross-boundary scheduler state.

Boundary ownership

Boundary
  inventory: ScanTargetInventory
  report: TitusReport
  credentials: CredentialsDocument
  scan()
  judge()
  extract()
  checkpoint()

The Boundary owns its persistent OS-managed lock file and its checkpoint. Target results, credential verdicts, extraction metadata, and the inventory publication flag are the durable work state; no separate phase-readiness document is needed.

Loading is owning

workspace.boundaries
  → unloaded Boundary paths sharing one backend

boundary.scan() / judge() / extract()
  → acquire OS lock
  → load current documents
  → run exactly one operation and cleanup
  → release ownership
  1. Construct unloaded Boundary objects from persisted boundary.json records; inventory commands first reconcile remotely discovered boundaries.
  2. Acquire the persistent boundary-local .operation.lock with an exclusive OS lock.
  3. Load current state only after ownership is acquired, then run exactly one requested operation.
  4. Mutate the in-memory aggregate and call Boundary.checkpoint().
  5. Close the reader and release ownership after operation cleanup. The lock file remains; ownership is the OS lock, not file existence.

Implemented execution model: one invocation may process different boundaries concurrently, but competing commands cannot overlap on the same boundary. Inventory creates no content services. Every Scan, Judge, or Extract operation creates one reader, scanner, judge, and extractor, then the requested command uses the services it needs. The scanner processes targets sequentially with at most one Titus invocation at a time; Titus's internal parallelism remains available. Each target is checkpointed before the next starts.

The design rule is to keep module responsibilities clear and avoid circular dependencies; specific import directions are implementation choices. In the current implementation, Boundary uses its owner's concrete Workspace, backend content readers receive a scratch context, and Boundary's type-only Workspace reference avoids a runtime cycle. These details describe the current structure rather than prescribing a permanent import hierarchy.

Workspace owns one configured backend and constructs unloaded Boundaries from persisted boundary records. Inventory commands first discover remote boundary IDs and reconcile availability without constructing content services. Source-dependent operations acquire the boundary OS lock before loading state and create the boundary's reader, scanner, judge, and extractor together; the requested command uses only what it needs. Different boundaries may run concurrently. Scan targets and retries run sequentially and share the boundary datastore. Titus internal workers remain supported, and Titus inherits the lock descriptor. Scan, judge, and extract commands run in separate Python processes, without a source-content cache.

Publication and crash recovery

publication pending
  → target checkpoints
  → final report.json
  → merged credentials.json
  → publication complete
  → judgment stage
  → extraction stage

Inventory/report/credentials are separate atomic checkpoints, not one transaction. A crash after target completion still requires export. A crash before publication conservatively repeats export/merge without rescanning completed targets or resetting saved judgments/evidence.

A crash after a saved VALID or UNKNOWN judgment resumes evidence without rejudgment. If bytes were written but metadata was not, retrieval of the same immutable first occurrence permits adoption only when existing bytes match. Conflicting bytes fail visibly and are never overwritten. This is crash-gap recovery, not an audit of RETAINED credentials.

Reconciliation and resource recovery

At boundary-session entry, validate the selected inventory and document identities. Target, judgment, and extraction status are read from their canonical documents. Invalid schemas, missing required documents, and mismatched identities fail explicitly.

There is no standalone stage scheduler or READY/IDLE state. A later explicit scan command sees publication intent in inventory and republishes the cumulative datastore without rescanning completed targets.

The persistent .operation.lock file is never used as a sentinel and is never removed during normal operation. Exclusive OS locking determines ownership, so process death releases ownership without stale-lock recovery.

Titus inherits the lock descriptor. If a child survives its parent, it continues to exclude another command from the boundary until the descriptor closes.

Upgrade / Part of each persisted-format change

Migrate the one existing workspace with each format change.

This is a single-user project with one existing workspace. A change to its persisted format includes migrating that workspace in the same task, preserving accumulated results and evidence. Migration should address the actual workspace; no general compatibility framework for a hypothetical installed user base is required. The commands below describe the current migration utility, which must be adapted when needed.

Stop all commands and any surviving old Titus subprocesses before upgrading. The old workspace is expected to have no lock files. Back up the complete workspace, including the datastore, before applying the upgrade.

Current contracts are boundary record 1 · scan targets 11 · report 2 · credentials 8. Runtime commands do not require an execution checkpoint; boundary availability, target, judgment, extraction, and publication state are the source of truth.

uv run --locked python -m cred_scan.tools.migrate_workspace_schema WORKSPACE --dry-run
# Back up the complete workspace before applying:
uv run --locked python -m cred_scan.tools.migrate_workspace_schema WORKSPACE --apply

The offline migration upgrades legacy inventory versions 8, 9, or 10 to scantargets.json version 11 and creates boundary.json version 1. It backs up and removes the original inventory.json. Obsolete scan targets may be removed under the latest-only rule, while historical credentials, occurrence paths, judgments, evidence, and cumulative scan data remain preserved. A boundary with an existing Titus datastore is marked publication pending so its next explicit scan command performs one conservative export and merge without rescanning completed targets.

For each upgraded boundary, write scan targets and the boundary record only after all related documents validate. The tool itself does not scan, call an LLM, download content, audit evidence, or modify reports, credentials, evidence, or datastores.

There is no runtime migration, old-field alias, or automatic legacy default. A partially upgraded workspace must finish migration before normal commands run. Rollback uses a coherent workspace backup.

04 / Persistence & ownership

What stays, what changes, what is temporary.

One backend → one report boundary → its selected scan targets and retained artifacts. Documents never combine findings from different boundaries. Inventory, report, judgment, and extraction writes are individual checkpoints, not a multi-document transaction.

Scan, judge, and extract directly mutate their owned in-memory Pydantic objects. Updates and merges do not copy models to preserve previous in-memory state. Discovery and candidate conversion finish before their results are applied. At each checkpoint, Boundary functions serialize every available document completely into the workspace, replacing each file atomically. Exceptions: Titus writes its cumulative datastore during scanning, and the extractor writes retained evidence bytes before Boundary checkpoints their extraction metadata.

Scheduling and handoff

  • Each per-boundary command operation holds exclusive ownership from state load through cleanup. One invocation may process different boundaries concurrently.
  • Inventory creates no content services. Scan, Judge, and Extract each create the boundary reader, scanner, judge, and extractor together; the requested command uses what it needs. Scan targets and Titus invocations run sequentially; Titus itself may use internal parallelism.
  • A single TitusCliScanner serves each boundary. There is no scan_concurrency setting; internal_workers controls Titus internal parallelism. Retry transient scan failures up to three attempts; permanent failures do not retry. Checkpoint each completed scan target before starting the next.
  • Scan, judge, and extract run as separate commands. Completed scan work is skipped; extraction checks retained evidence even when no new extraction is pending.
  • Absent boundaries and already-scanned targets do not start new scans. Removed scopes and replaced versions are absent from current scan targets.

Retention and failure rules

  • Append publication preserves old credentials, locator occurrences, judgments, and evidence metadata—even if a later report omits them.
  • Scan, judge, and extract run in separate Python processes. Readers do not cache resolved locations or retrieved content. Temporary downloads are removed after use; retained evidence is persisted independently. Whole-image, repository, archive, and general blob caches are forbidden.
  • Agreed design: check only that each RETAINED file exists on later runs. Report missing files without automatic replacement. Do not verify contents, size, or hash. Extraction checks RETAINED records even when no new evidence is pending.
  • A saved VALID or UNKNOWN judgment survives a later extraction error, so extraction can retry without another LLM judgment.

05 / Walk one credential through

Repository → scan target → occurrence path → evidence.

Schematic identifiers below describe the boundary inventory and backend locator flow. No credential value is shown.

  1. Inventory. The Artifactory backend discovers repository docker-local, image scope payments/api, and selected child manifest M1. It writes a ScanTargetInventory owned by the repository and containing a ScanTarget whose scope is a DockerImageScanScope at immutable manifest M1.
  2. Scan. The target is scanned into that boundary’s titus.ds. After all eligible targets finish, the final TitusReport contains a finding at app.env. Conversion retains its complete backend locator as a credential occurrence.
  3. Publish. Conversion creates credential C1, with one CredentialOccurrence containing the complete backend locator. Its JudgmentResult starts PENDING and extraction is null. After exclusions, merge and persist the CredentialsDocument. Only now may it reach Judge.
  4. Judge. The judge receives C1 and a content reader. Assume it returns JudgmentResult(verdict="VALID", reasoning=…). Orchestration saves this result to the latest credentials.json.
  5. Extract. Read app.env through the extraction command’s reader. Retain the file under C1’s evidence directory and save ExtractionResult(status="RETAINED", output_path=…, size=…, sha256=…). The Boundary closes the reader at lifecycle end.
  6. Mixed obligations and recovery. Suppose another historical credential is ERROR and a third is VALID with extraction ERROR when M2 is discovered. Explicit scan, judge, and extract commands each find their own persisted work. Scan finishes M2's publication; later judgment and extraction commands independently reload the boundary. A crash with all targets scanned but publication still pending resumes export rather than rescanning completed scan targets.
  7. Next inventory, next scan. A scan target for child manifest M2 replaces M1 in inventory. The cumulative Titus datastore and historical credentials remain. Self-contained occurrence paths allow the backend to read M1 without its old inventory entry. If C1 appears at another locator in M2, append its occurrence without changing the first evidence location. Keep RETAINED metadata and check only that its file exists; report absence without automatic replacement. A new missing/error extraction still uses the immutable first occurrence.
